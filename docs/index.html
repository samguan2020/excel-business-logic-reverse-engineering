Finance Excel Reverse Engineering

Microsoft IQ describes an enterprise intelligence layer — Work IQ, Fabric IQ, Foundry IQ, Web IQ — as a managed platform capability. This project asks: what does an IQ-inspired workflow look like built entirely from open-source substitutes, with no calls to those services at all, applied to a concrete task — turning spreadsheet formulas into business-readable documentation and migration drafts?

An independent experimental prototype, not an official Microsoft implementation, a financial calculation engine, or a production migration tool. Generated explanations, requirements, and code require human review.

Processing flow

From a workbook to a reviewed Markdown report

Given an .xlsx workbook, the pipeline extracts structure, gathers local context, documents each sheet, and compiles the result — to a CLI file or a Teams Adaptive Card with consent-based upload.

Extract

Cells, formulas, references, and a dependency graph via openpyxl + formulas + NetworkX.

Gather context

Local glossary, workbook comments, author/collaboration metadata.

Document per sheet

Retrieve local context; fall back to a web query only when retrieval looks weak.

Compile

Dependency narrative, draft migration assets, and a Markdown report — CLI file or Teams card.

Engineering decisions

Precision about the boundary is the actual deliverable

Why reference-parsing over regex

The formulas parser expands supported ranges and understands cell references structurally. The graph records dependencies, not evaluated financial results — a dependency graph is not proof of computational equivalence.

Why three swappable model backends

Ollama (local), an OpenAI-compatible endpoint, or Microsoft Foundry via AnthropicFoundry + DefaultAzureCredential — model choice and model licensing are kept separate from the open-source application libraries themselves.

Why an async job API instead of a long-lived request

A sequence of model calls can take minutes. POST /analyze returns a job ID immediately; the client polls GET /analyze/{job_id} instead of holding one HTTP connection open.

Why the Teams bot is optional

The Python CLI works without a Microsoft 365 tenant at all. The Teams SDK front end (@microsoft/teams.apps, pinned to 2.0.5) is an additive channel, not a dependency of the core pipeline.

Limitations, stated up front

What this does not claim

Formula parsing is not complete Excel execution — macros, external references, and dynamic behavior need additional validation.

No per-user isolation or enterprise document-permission enforcement; allowed_sources is a metadata filter, not an authorization mechanism.

Search snippets ground generation, but source-linked citations in the report are not guaranteed.

The API job store and bot report cache are in-memory — restarting the process loses job state; this is not a durable queue.

Model-generated requirements and starter code are drafts — review and test before relying on them for financial decisions.
